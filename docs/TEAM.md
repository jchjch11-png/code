# 팀 구성과 업무 배정

작성일: 2026-11-24. 총 7개 역할: 메인 1명, Astra 3명, Sol 3명.

## 실제 생성한 팀

## 배정 이유

- Astra는 OS별 제약, 날짜·동시성 계약, 출시 판단처럼 복수 조건을 검토하는 역할에 배정한다.
- Sol은 합의된 계약을 바탕으로 기능을 구체화하고 화면·데이터·문구를 일관되게 구현하는 역할에 배정한다.
- 이 구분은 책임 배분이며 특정 모델의 산출물을 검증 없이 신뢰한다는 뜻이 아니다. 모든 역할은 검토를 거친다.

## 리뷰와 인수인계

| 작업 | 작성 책임 | 검토 책임 | 다음 수신자 |
|---|---|---|---|
| 공통 구조·인터페이스 | 아키텍처 | 메인, 도메인·알림 담당 | 전체 팀 |
| 목표·섭취·보상·저장 | 도메인·데이터 | 아키텍처, 품질·출시 | 알림, UX |
| 예약·알림 버튼 | 네이티브 알림 | 아키텍처, 도메인·데이터, 품질·출시 | UX, 현지화 |
| 화면·스티커 | UX·스티커 | 현지화, 품질·출시 | 메인 |
| 언어팩·형식 | 현지화 | UX, 품질·출시; 출시 문구는 언어 검수 | 알림, UX, 출시 |
| 시험·정식 배포 자료 | 품질·출시 | 메인, 관련 담당 | 실제 배포 담당 및 사용자 |

작성자는 자신의 실행 결과를 기록한다. 품질 담당은 중요 경계와 증거를 별도로 검토한다. 메인은 요구사항 누락과 담당 간 충돌을 해소한다.

## 업무 시작 규칙

1. 메인이 단계, 요구사항 ID, 소유 파일, 선행 조건, 산출물, 완료 기준을 함께 배정한다.
2. 담당자는 공통 문서와 소유 업무지침을 읽고 필요한 계약 변경을 알린다.
3. 담당 파일만 수정하고 변경·검증·남은 사항을 보고한다. 병렬 작업은 소유권이 겹치지 않을 때 진행한다.
4. 리뷰를 거쳐 메인이 통합하고 STATUS.md를 갱신한다. 차단된 작업이 있어도 독립 작업은 계속한다.

최초 시제품 구현에서는 메인이 공유 설정·앱 화면·플랫폼·현지화·문서를 통합했다. 각 업무지침의 S0 코드 경로는 제안이며, 구현 여부는 STATUS와 실제 파일을 기준으로 한다.

## 최초 시제품의 실제 투입

- 메인 `/root`: Flutter 기반, 화면·언어팩, 네이티브 알림 통합, 검사·빌드·GitHub 저장·보고.
- `/root/domain_impl` · `gpt-6.2-sol`: `lib/domain/models.dart`, `lib/data/hydration_repository.dart`, `test/hydration_repository_test.dart` 구현 후 메인에 인계.
- `/root/notification_review` · `gpt-6.2-astra`: 알림 코드만 집중 검토. iOS delegate, 재실행 후 버튼의 실제 용량, 권한 대기 중 날짜·예약 시각 경계의 세 가지 문제를 지적했고 메인이 수정했다.
- 구현은 메인과 Sol 1명 중심으로 수행했다. Astra 검토는 한정된 과업이었으며 실기기 테스트를 대신하지 않는다. 위 하위 과업은 인계를 마쳤다.

## 인수인계 보고 양식

```text
담당 / 단계 / 요구사항 ID:
상태: TODO | IN_PROGRESS | REVIEW | DONE | BLOCKED
변경 파일:
핵심 결정과 인터페이스 변경:
수행한 검증 및 증거:
수행하지 못한 검증과 이유:
다음 담당자 / 필요한 입력:
```

사용자에게는 현재 단계, 실제 완료 결과, 확인이 필요한 항목만 간결하게 보고한다. 문서 완료와 앱 개발 완료를 구분한다.
