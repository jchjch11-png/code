# 도메인·데이터 업무지침서

## 역할과 소유권

- 담당은 Sol 도메인·데이터다. 하루 목표, 음용 기록과 합계, 보상·달력 상태, 알림 액션의 데이터 계약을 맡는다.
- S0에서 소유하는 파일은 이 문서다. 제품 범위와 수용 기준은 [제품 요구사항](../PRODUCT.md)을 따른다.
- 구현 승인 후 목표·섭취량·일일 원장·보상 규칙, 로컬 저장소 구현과 스키마, 마이그레이션 및 도메인 테스트를 맡는다.
- 구현 파일 경로와 인터페이스의 편집 담당은 S1에서 메인이 배정한다. 공용 설정과 의존성 변경은 메인이 통합한다.
- 아키텍처 담당과 저장 엔진·트랜잭션·시간 공급자 계약을 맞추고, 알림 담당에 예약 입력과 액션 처리 결과를 전달한다.
- UX·보상 담당과 편집·복구·스티커 표시 상태를 맞추고, 현지화 담당에게 단위 값과 문구 키에 필요한 정보를 전달한다.
- 아래 모델과 처리 방식은 S0 제안이다. 공통 계약 승인, 구현, 자동 검사, 실기기 검증은 각각 별도로 기록한다.

## 목표와 음용량

### 최초 시제품에서 확정한 계약

- 아래 S0 정책 제안 중 목표 변경 시점은 시제품에서 **오늘과 이후 날짜에 즉시 적용**하는 것으로 정했다. 목표 입력 화면에도 이 범위를 표시한다. 과거 날짜의 목표 스냅샷은 바꾸지 않는다.
- 저장은 SQLite, 입력은 정수 mL이며 목표와 1회 직접 입력의 기술적 허용 범위는 1~20,000mL다. 이 범위는 권장 섭취량이 아니다. fl oz·프로필·복구·전체 삭제는 아직 구현하지 않았다.
- 알림 회차의 고유 섭취 키와 트랜잭션으로 전체·절반 중 한 건만 기록한다. 삭제된 기록은 재전달로 복원하지 않는다. 별도 ActionReceipt 테이블 대신 회차 상태·고유 키·삭제 표시를 사용한다.
- 앱의 현재 기기 날짜에 기록을 귀속하고 UTC 시각과 날짜 키를 저장한다. 시간대 식별자 별도 저장과 여행·DST의 실기기 검증은 후속 작업이다.
- 구현은 `lib/domain/models.dart`, `lib/data/hydration_repository.dart`, 검사는 `test/hydration_repository_test.dart`에 있다. 아래 나머지 항목은 전체 제품 계획이다.

- 앱에 기록한 음료의 음용량과 음식 수분을 포함할 수 있는 총수분 섭취량을 구분한다. 건강 권장치의 출처마다 지표와 적용 대상이 다를 수 있다.
- 몸무게·성별·나이·활동량 등 프로필 입력을 받을 수 있게 설계하되, 근거 검토 전에는 계수·숫자 공식·범용 기본량을 정하지 않는다.
- 권장 기능의 근거, 적용 연령·집단, 예외 및 총수분에서 음용 목표로 옮기는 기준을 검토한 뒤 권장 로직과 문구를 확정한다.
- 사용자가 하루 음용 목표를 직접 입력할 수 있게 한다. 처방받은 목표도 직접 입력 경로에서 설정할 수 있다.
- 권장 근거를 확정하기 전에는 직접 목표 설정으로 진행할 수 있게 하고, 근거 확보를 출시 권장 기능의 별도 결정으로 추적한다.
- 프로필은 목적에 필요한 항목만 기기에 저장한다. 출시 초기에는 로그인과 계정 동기화 없는 기기 내 저장을 가정한다.

## 초기 데이터 모델

| 레코드 | 주요 필드와 계약 |
| --- | --- |
| Profile | 선택 입력인 몸무게·성별·나이·활동량, 업데이트 시각. 입력 항목은 근거·개인정보 검토 후 확정 |
| Settings | 언어 선택, 단위 표시, 목표 설정, 기상·취침·조용한 시간, 자동·수동 알림 설정, 설정 버전 |
| Goal | 양(mL), 출처(직접·권장), 근거 버전(권장 시), 적용 시작일 |
| DailyLedger | 날짜 키, 하루 목표 스냅샷(mL), 스냅샷 시점·출처, 날짜 경계에 사용한 시간대 정보 |
| IntakeEntry | 기록 ID, 발생 UTC 시각, 귀속 날짜·입력 시 시간대, 양(mL), 입력 출처, 생성·수정 시각, 알림 발생 ID(선택) |
| ReminderOccurrence | 발생 ID(occurrenceId), 예약 개정 번호(revision), 귀속 날짜, 예정 시각, 예정량(mL), 상태 |
| ActionReceipt | 고유 키(occurrenceId, revision, action), 결과(기록·미루기·건너뛰기·만료 등), 관련 기록 ID(선택), 처리 시각 |
| DailyReward | 날짜 키, 등급, 캐릭터 자산 ID, 배치 여부, 날짜 칸 안의 위치(선택) |

- 스키마 버전과 설정 버전은 용도를 분리한다. 식별자는 앱 재실행과 예약 갱신 이후에도 동일한 레코드를 가리켜야 한다.
- 저장 단위는 양의 정수 mL를 초기안으로 두고 S1에서 검증한다. 빈 값·0·음수와 저장 범위를 넘는 변환 결과를 거부하며, 현실적인 입력 범위는 제품에서 확정한다.
- 국제 단위계와 미국 액량 온스(US fl oz)를 지원한다. 변환에는 1 US fl oz = 29.5735295625 mL를 사용한다.
- fl oz 직접 입력은 입력 시 한 번 정수 mL로 반올림한다. 같은 값이라면 중간값을 올리며, 표시용 반올림 값을 다시 저장하지 않는다.
- 기본 표시 제안은 mL 정수와 fl oz 소수 첫째 자리다. 지역별 숫자 형식을 쓰며, 반 컵은 해당 알림에 저장된 예정량의 절반을 mL 정수로 반올림한다.
- 예를 들어 251 mL의 반 컵은 126 mL다. 1 mL 예정량에서는 전체와 절반 결과가 모두 1 mL이므로 알림 액션 중복 표시 여부를 시제품에서 확인한다.
- 목표 대비 화면 수치는 상한을 두더라도 실제 합계는 그대로 유지한다. 100%에 못 미치는 값을 진행률 표시 반올림으로 100%로 표시하지 않는다.
- 언어, 지역 형식, 단위, 시간대는 각기 설정 또는 시스템 정보에서 해석한다. 초기 언어팩은 en, zh-Hans, zh-Hant, ja, ko, hi다.

## 날짜 경계와 하루 목표

- 날짜 키는 YYYY-MM-DD다. 새 섭취를 기록할 때 적용 중인 기기 시간대로 날짜를 산출하고 UTC 시각과 당시 시간대 식별자 또는 오프셋을 함께 저장한다.
- 과거 기록과 보상은 저장된 날짜에 유지한다. 시간대 변경으로 이미 기록이 있는 날짜에 진입하면 해당 일일 원장과 스냅샷을 이어 쓴다.
- 자정은 현지 달력 날짜의 전환으로 판단한다. 일광절약시간 전환 때문에 하루 길이가 달라도 다음 날짜를 UTC 24시간 간격으로 계산하지 않는다.
- 앱 재개와 자정, 시간대 변경 때 오늘의 날짜 키를 다시 계산한다. 미래 알림은 새 시간대에서 현지 설정을 다시 적용해 재평가한다.
- 일일 원장을 처음 사용할 때 그날에 적용할 목표를 복사해 저장한다. 오늘의 목표 변경은 다음 현지 날짜부터 적용하는 정책을 제안한다.
- 첫 목표 설정은 당일 즉시 적용한다. 오늘 사용한 스냅샷과 과거 보상에는 이후 설정을 소급 적용하지 않는다.
- 과거 신규 입력에는 그 날짜의 기존 스냅샷을 사용한다. 원장이 없으면 해당 날짜의 목표 이력을 적용하고, 이력이 없으면 사용자가 그 날짜 목표를 직접 입력하도록 한다.
- 자정이 지나면 해당 일자의 결과를 집계해 계속 표시한다. 이후 사용자 수정·삭제·복구가 있으면 그 날짜 결과를 다시 계산한다.

## 기록과 알림 액션

- 직접 입력, 전체·반 컵, 수정, 삭제, 복구는 같은 원장을 갱신한다. 제거된 기록은 합계에서 제외한다.
- 알림 메시지와 액션 페이로드는 발생 ID·개정 번호·귀속 날짜·예정량으로 연결한다. 실제 표시될 전체량과 절반량은 공통 변환 규칙으로 제공한다.
- 전체·절반 섭취 기록은 발생 ID의 전체 수명에서 최대 한 번만 확정하도록 저장소에 고유 제약을 건다. 건너뛰기는 해당 발생을 종료한다.
- 미루기와 언어 변경은 발생 ID를 유지하고 개정 번호를 올린다. 미루기 후에도 새 개정의 섭취 액션을 처리할 수 있다.
- 같은 발생 ID·개정 번호·액션이 재전달되면 영수증의 최초 결과를 반환한다. 유효한 영수증이 없는 이전 개정의 액션은 만료 처리해 섭취를 생성하지 않는다.
- 액션의 영수증, 섭취 기록과 일일 보상 갱신은 하나의 로컬 트랜잭션에 넣는다. 삭제한 알림 기록의 액션 영수증은 유지해 재전달로 기록이 살아나는 일을 막는다.
- OS 예약 변경은 로컬 저장과 원자적으로 묶이지 않는다. 저장한 일정 의도와 예약 결과를 대조해 실패 시 재실행하고, 앱 재개에서 차이를 복구한다.
- 레코드를 찾을 수 없거나 취소·만료되었거나, 발생 날짜가 현재 날짜보다 이전인 알림 액션은 자동 기록 없이 처리한다. 필요하면 앱의 해당 날짜 직접 편집으로 연결한다.
- 예정일이 현재 날짜보다 미래인 알림 액션도 만료·무효로 보고 시간대 이동 뒤 잘못 저장되는 것을 막는다.
- 도메인 계층은 자동 배치의 순수 규칙과 예정량 계산을 맡는다. 알림 가능 시간만 사용하고 마지막 예정량으로 목표·회당 용량의 나머지를 처리한다. 실패·건너뛰기로 생긴 양을 시간대 끝에 몰아 배치하지 않는다.
- 네이티브 계층은 도메인이 산출한 일정의 OS 예약, 액션 콜백 전달, OS 예약 상태 복구를 맡는다.
- 오늘 목표 달성 시 그날 남은 알림을 취소한다. 오늘 기록의 삭제·취소·감액으로 다시 목표 미달이면 향후 허용 구간의 알림을 재평가한다.
- 재평가는 지난 슬롯과 사용자가 건너뛴 슬롯을 되살리지 않는다. 허용 시간이 남지 않았으면 다음 날짜부터 정상 일정을 이어간다. 과거 기록 수정은 오늘 일정에 영향이 없다.

## 보상과 스티커 배치

- 날짜별 합계 ÷ 해당 날짜의 목표 스냅샷으로 등급을 결정한다. 정수 비교로 경계를 판정해 표시용 반올림이 보상에 영향을 주지 않게 한다.
- 50% 미만은 스티커 없음, 50% 이상 80% 미만은 엉뚱한 캐릭터, 80% 이상 100% 미만은 두 번째 등급, 100% 이상은 특별 스티커다.
- 100% 초과에 추가 보상은 없다. 날짜 하나에 유효한 보상 하나를 산출하고 당일·과거 기록의 편집이나 복구 때 모두 같은 규칙으로 재계산한다.
- 스티커는 획득한 날짜 칸에만 붙인다. 칸의 크기가 바뀌어도 위치를 보존할 수 있도록 상대 좌표를 저장한다.
- 등급이 바뀌면 스티커 자산을 갱신하고 배치된 스티커의 위치를 유지한다. 50% 미만이 되면 스티커를 숨기고 배치를 해제한다.
- 다시 50%에 도달하면 배치 전 상태의 보상을 새로 표시한다. 위치 삭제 또는 등급 변경 시 UX에서 재계산 결과를 알 수 있게 한다.

## 저장, 개인정보와 장애 복구

- 앱 재시작 이후 프로필·설정·기록·보상·배치를 복구할 수 있는 버전 관리 로컬 저장소를 선택한다.
- 기록 삭제 및 되돌리기의 보존 기간·종료 조건을 S1에서 정한다. 전체 데이터 삭제는 삭제 의도를 저장하고 앱 소유 예약과 데이터를 지우는 재실행 가능한 절차로 설계한다.
- 전체 삭제 범위에는 프로필·설정·스냅샷·기록·보상·배치·액션 영수증이 포함된다. 이전에 발급한 알림 액션으로 새 데이터를 생성하지 않도록 예약 식별자 재사용을 피한다.
- 시스템 자동 백업의 적용 여부와 복원 시 규칙을 출시 전 결정한다. 문제 진단 기록에 프로필이나 섭취 원본을 넣지 않는다.
- 스키마 변경마다 이전 공개 스키마에서 전환하는 경로를 작성한다. 기존 ID, 날짜, 목표, 양, 액션 키, 스티커 위치를 보존한다.
- 마이그레이션은 가능한 범위에서 트랜잭션으로 실행한다. 실패 시 원본을 보존하고 재시작 또는 재시도에 같은 결과를 얻을 수 있게 한다.
- 손상·디스크 부족·예약 재동기화 실패를 분리해 처리한다. 복구가 필요한 저장 오류는 사용자에게 알리고 초기화 전에 데이터를 보존한다.

| S2 알림시제품 | 플랫폼 액션 전달과 재전달, 정수 mL 페이로드, 저장·OS 예약 재조정 확인 |
| S3 전체기능·지역화 | 직접 목표·기록·수정·달력 구현과 6개 로캘에서 날짜·단위·보상 상태 연결 |
| S4 실기기QA | 4종 기기에서 기록 보존, 날짜 경계, 권한·재전달·오프라인 결과를 QA에 인계 |
| S5 시험배포 | 업데이트 마이그레이션과 장애 복구 리허설, 시험 사용자 기록 흐름 확인 |
| S6 출시빌드·자료 | 저장·삭제·백업 실제 동작과 개인정보·건강 기능 설명을 대조 |
| S7 심사·공개 | 승인 범위 내 공개 빌드의 신규 설치·업데이트·기록 흐름 확인 |
| S8 운영 | 데이터 이슈 재현, 스키마 호환성 및 권장 목표 근거 변경 관리 |

- 자동 검증 후보는 단위 변환·홀수 절반, 50/80/100% 경계, 목표 변경 전후 원장, 오래된 알림과 중복·동시 액션이다.
- 미루기 직후 이전 개정의 버튼이 재전달돼도 기록이 생기지 않고, 같은 발생 ID의 새 개정에서 반 컵을 누르면 한 건만 기록되는지 확인한다.
- 날짜 사례는 자정 직전·직후, 일광절약시간 전환, 시간대 이동·재진입, 목표 이력 없는 과거 기록을 포함한다.
- 상태 검증은 목표 달성 직후 기록 취소, 과거 등급 하락과 스티커 위치 처리, 재시작·마이그레이션·저장 실패 후 복구를 포함한다.
- UX에는 목표 출처·기록 상태·보상·배치 상태를, 알림에는 예약 의도·액션 결과·재평가 조건을 전달한다. 현지화에는 실제 mL과 변환·날짜 표시 규칙을 전달한다.
- S1에서 목표 정책, 입력 범위, 예약 만료·특수 시각 처리, 삭제·백업 및 데이터 모델을 메인과 합의한다. 건강 권장 근거는 로직 구현 전에 별도로 확정한다.
- S2 이후 인수인계 기록에는 확인한 버전, 재현 입력과 실제 관찰값, 자동 검사·실기기 상태, 미해결 항목과 담당을 남긴다.
